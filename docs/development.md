# Firefly 开发约定

本文约束 Firefly 仓库中的分支、提交和架构演进。目标是让每次变更都容易审查、验证、回退和合并。

## 分支命名

所有新工作从最新 `master` 创建独立分支，名称使用小写短横线：

| 类型 | 用途 | 示例 |
| --- | --- | --- |
| `future-` | 新能力、行为扩展或架构演进 | `future-admin-hardening-v1.0.2` |
| `fixed-` | 缺陷修复 | `fixed-outbox-claim-race-v1.0.2` |
| `doc-` | 仅文档变更 | `doc-development-workflow-v1.0.2` |
| `script-` | 构建、发布、运维或辅助脚本 | `script-release-check-v1.0.2` |

版本后缀不是强制项；属于明确版本增量时使用 `-vX.Y.Z`。一个分支只承担一个可描述的主题，避免把无关重构、功能和修复混在一起。

每个主题通过独立 PR 直接合入 `master`，不创建版本集成分支。版本范围内的所有 PR 合并并在
`master` 完成回归后，才创建对应 tag 和 GitHub Release。

## 提交粒度

- 每个提交只表达一个可独立解释和验证的意图。
- 结构重构与行为变化尽量分成不同提交；先保持行为完成拆分，再增加新策略。
- 每个提交前运行与改动范围匹配的测试，合并前运行受影响模块的完整测试。
- 不顺手格式化或重命名无关文件，不提交 `node_modules`、构建目录、日志和本地数据库。
- 提交信息使用 `feat:`、`fix:`、`refactor:`、`test:`、`docs:`、`build:` 等明确前缀。
- 一个功能允许多段提交，不以压缩提交数量为目标；优先保证单次改动量可审查、可回退。

## 设计原则

### 领域与抽象

- 调度、执行、租约、派发、插件等领域规则放在各自边界内，不让 HTTP、Netty 或 JDBC 细节进入调度核心。
- 可以采用 DDD、Strategy、Policy、Factory、Coordinator、Adapter 等模式，但只有在它们能明确职责、隔离变化或消除条件分支时引入。
- 避免为简单数据流建立过多接口、实体和包装层。抽象数量应与真实变化点匹配。
- `libs/scheduler-core` 保持纯 Java，不依赖 Web 框架、Guice、Netty 或具体数据库。

### 通信边界

- Admin API 继续使用 JDK `HttpServer`，通过内部 Router、Filter、Controller 和统一请求上下文改善可维护性，不引入大型 Web 框架。
- Netty 用于 Executor 长连接、Gateway 转发和高频低延迟通信。
- OkHttp 用于需要 HTTP 语义的客户端或服务间调用；不使用它替代 Netty 的长连接执行通道。
- 协议模型、编解码、Gateway 运行时和业务侧 Client 保持独立依赖方向。

### 并发与背压

- 生产线程池必须有明确容量、命名、关闭流程、监控和拒绝语义。
- 默认不使用无界队列，也不允许静默丢弃任务。
- 可重试工作采用类似消息队列的“有限等待后重试”策略：等待时间、最大尝试次数和退避必须有上限，且关闭过程能够立即终止等待。
- 不能在 Netty EventLoop、Scheduler timer 或 HTTP 接收线程中执行阻塞重试；重试必须交给独立协调器或持久化队列。
- 达到最终拒绝条件后必须返回可观察结果，并记录指标；是否进入持久化失败登记由具体领域语义决定。

“失败注册”目前只作为设计候选，不在 1.0.2 中直接实现。后续需要先定义登记对象、去重键、生命周期、重放时机和清理策略，避免形成另一个没有明确消费方的失败表。

## 质量门禁

- 新行为必须有正常路径、边界条件和失败路径测试。
- JDBC 一致性变更至少覆盖 H2，并在真实 PostgreSQL/MySQL CI 中覆盖方言或并发差异。
- 协议变更必须定义版本兼容策略，并覆盖新旧端组合。
- 数据库迁移必须可重复验证，升级路径不能用全量初始化脚本代替。
- 公共 API、配置项、数据库字段和运维步骤发生变化时，同一分支同步更新文档。
