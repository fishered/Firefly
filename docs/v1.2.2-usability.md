# Firefly v1.2.2 首次接入与运维诊断闭环

状态：实现中。本文记录本次代码交付与仍需满足的发布门禁，不把未验证的目标写成已达成。

## 用户路径

管理台按“接入 → 创建 → 运行 → 诊断 → 调整”组织工作，而非要求用户从技术模块拼接流程。

| 阶段 | 入口 | 已实现行为 |
| --- | --- | --- |
| 接入 | 首次接入 | 复用 Overview、Nodes、Executors、Integration Key、Jobs、Executions API 展示七项就绪检查，生成可复制的 Spring Boot YAML |
| 创建 | 任务管理 | 四步任务向导：执行目标、调度规则、资源策略、预览确认；高级分发策略默认折叠 |
| 运行 | 待处理中心 | 汇总当前已加载页面的失败执行、离线执行器、派发死信、失败事件、异常补数、租户配额风险和节点异常 |
| 诊断 | 执行详情 | 读取既有 Execution timeline API，按触发、配额准入、Outbox、Gateway、ACK、执行、重试/重放组织时间线；无持久化时间戳的阶段显示“暂无观测数据” |
| 调整 | 任务编辑、租户治理 | 变更先预览；表单变化使预览失效；请求失败保留输入；任务和租户配额由后端 expectedVersion CAS 保护 |

导航分为总览、调度、运行、治理、系统五组，原有视图仍以二级入口保留。全局搜索在已授权的现有列表 API 中查找 Job、Execution、Executor、Tenant。视图和执行筛选条件写入 URL，刷新后可恢复。

## 架构边界

本次没有改调度协议或数据库 Schema。Job 读取模型增加现有数据库 `version` 字段，Admin PUT 可选接收 `expectedVersion`；旧客户端仍可按原请求方式更新。Node 管理台继续代理 Java Admin API，浏览器不直接连接 Gateway。接入检查基于已有 Admin 读模型，不进行额外写操作，也不展示 Integration Key 明文。YAML 使用环境变量占位符，用户需填入实际服务名、Gateway 和 API 地址。

待处理中心是多个有界列表的前端聚合视图，不是全量告警索引。它当前遵守各 API 的第一页与分页上限，不能代表集群全历史总量。诊断时间线使用 `GET /api/executions/{id}/timeline` 的重建事件，只把快照中有证据的时间点标为已观测；配额准入和 Outbox 的精确事件尚未持久化，因此明确显示缺口。

任务编辑的预览是前端差异展示，提交时以 `expectedVersion` 做服务端原子比较；冲突返回 409，管理台保留原表单。现有 `firefly_job.version` 也随调度游标推进，故活跃任务的预览可能因调度而过期，需要重新打开任务读取新版本。这是安全但保守的冲突判断。

## 验收与发布门禁

- `npm run check` 和 `npm run test:e2e` 覆盖向导、待处理跳转、诊断时间线、URL 恢复及预览失效。
- `./gradlew --no-parallel check verifyPluginCompatibilityMatrix` 覆盖 Java 回归与模块边界。
- GitHub Actions 的 CI 执行上述 Node 与 Gradle 门禁，并在 Linux runner 上运行 Maven Spring Boot 兼容矩阵。
- 首次远程任务 10 分钟、普通任务 2 分钟、故障定位 60 秒是用户体验目标，必须在真实新环境与人工任务测试中测量；自动化测试不声称证明用时。
- 全量待处理查询、精确配额和 Outbox 事件时间戳仍是正式宣称“全链路诊断”前的未完成项。旧客户端未传 `expectedVersion` 时继续使用原有更新语义。

Maven Central、GHCR、官网发布只在版本号、标签、CI、兼容矩阵和真实部署验证全部通过后触发；本文件不构成发布记录。
