# Firefly v1.2.1 配额预演与容量规划

状态：实施完成，待发布。
设计日期：2026-11-07。

## 1. 版本决策

v1.2.1 聚焦“配额变更是否安全、应该配多少、为什么这样建议”。v1.2.0 已经解决多租户配额、全局准入、公平调度和拒绝可解释性；下一步不再扩展新的治理维度，而是把现有能力变成可预演、可度量、可审查的运营闭环。

候选方向按覆盖面、价值、确定性和实现成本评估如下：

| 候选方向 | 用户价值 | 实现风险 | 版本判断 |
| --- | --- | --- | --- |
| 配额 dry-run、容量基线和推荐 | 高：直接降低配额调整事故 | 中：复用 v1.2.0 权威用量 | **v1.2.1** |
| 弹性额度、突发积分 | 中高 | 高：改变准入语义和计费边界 | 后续版本 |
| 执行告警中心 | 高 | 高：属于 v2 Operations 主线 | 保留在 v2 |
| HTTP Executor、Python/Go SDK | 中 | 高：引入新协议与生态维护成本 | 继续后置 |

建议目标文本：

> 完成 Firefly v1.2.1 配额预演与容量规划：基于权威租户用量和有界历史观测，提供无副作用的配额 dry-run、容量基线、确定性推荐和 Admin 预览—应用闭环；所有结论可解释且带数据质量标记，不自动修改配额，不影响准入热路径，并保持与 v1.2.0 的数据、任务定义、Admin 默认用法和 Executor v1/v2 协议兼容。

## 2. 问题与成功标准

### 2.1 要解决的问题

运维人员当前可以动态修改配额，但在保存前无法回答：

- 新上限是否低于当前在用资源；
- 过去一段时间是否经常触顶；
- 降低配额会影响哪些资源维度；
- 当前配置是否长期闲置或缺少余量；
- 推荐值依据哪些观测得出，数据是否足够可信。

这会让配额调整依赖经验，容易造成新的准入拒绝，或者长期保留没有依据的无限配额。

### 2.2 发布成功标准

| 指标 | 目标 |
| --- | --- |
| dry-run 副作用 | 对 policy、usage、reservation、Outbox 和审计记录均为 0 写入 |
| 变更竞态 | 预览后 policy version 已变化时，应用必须返回 `409 tenant_version_conflict` |
| 结果可解释性 | 每个风险和建议均包含资源维度、观测值、阈值和稳定原因码 |
| 数据质量 | 覆盖率不足、当前配额截断或采集缺口必须返回 `UNKNOWN`，不得伪造精确预测 |
| 查询性能 | 1,000 个租户、7 天默认窗口的汇总报告 P95 小于 2 秒 |
| 热路径开销 | 准入事务不新增同步 JDBC 写；观测缓冲满时丢弃规划样本，不影响准入 |
| HA | 采集节点接管后不重复累计计数，最多丢失一个未刷新的观测桶 |
| 兼容性 | 1.2.0 节点可在滚动升级期间继续准入和派发；Executor wire protocol 不变 |

## 3. 必须交付

| 范围 | 必须交付 | 核心验收 |
| --- | --- | --- |
| 配额预演 | 单租户 proposed policy 校验；当前用量影响；历史风险；公平权重变化提示 | 请求不创建 reservation、不修改 policy；相同快照得到相同结果 |
| 容量基线 | 并发、CPU、内存、backlog、触发速率的当前值、平均值、峰值、触顶比例和拒绝数 | 数据带窗口、覆盖率、采样间隔和完整性等级 |
| 推荐配置 | 基于历史峰值与显式余量生成确定性建议；支持逐维度解释 | 数据不足或被现配额截断时不输出伪精确值 |
| 变更闭环 | Admin 中先预览再使用同一 `expectedVersion` 应用；展示 before/after diff | 预览过期不能覆盖并发修改；实际应用继续进入现有审计 |
| 运维报告 | 全租户风险排序、闲置/饱和/无限配额识别、JSON/CSV 导出 | 能回答“谁最可能被拒绝、为什么、建议怎么改” |
| 生产门禁 | 1,000 租户、7 天样本、HA 接管、滚动升级、并发配置更新、采集背压 | 不影响准入，不重复统计，不产生无界表增长 |

## 4. 产品语义

### 4.1 dry-run 不是 reservation

dry-run 只读取某一时刻的 policy、权威 usage 和历史容量样本，然后对 proposed policy 做纯计算。它不得调用 `tryReserve`，不得创建临时 reservation，也不得通过“申请后释放”的方式模拟。

请求必须携带 `expectedVersion`。响应返回同一个 `baseVersion`；应用仍复用 v1.2.0 的 `PUT /api/tenants/{tenantId}`。如果预览和应用之间版本变化，PUT 返回现有的 `409 tenant_version_conflict`，用户必须重新预览。

降低配额到当前用量以下不会终止运行中任务，也不阻止保存，但必须给出 `CURRENT_USAGE_ABOVE_PROPOSED_LIMIT` 的 `CRITICAL` 警告。保存后只影响新的准入。

### 4.2 历史观测不是容量承诺

历史数据用于描述已经观测到的负载，不预测未来业务增长。每个资源维度返回：

- `current`：预演时权威用量；
- `average`：窗口内采样平均值；
- `peak`：窗口内最高观测值；
- `saturationRatio`：有界配额下达到或超过 90% 的样本比例；
- `rejections`：窗口内该资源原因的拒绝次数；
- `coverageRatio`：实际观测桶数 / 预期桶数；
- `censored`：历史值是否可能被当时的配额截断。

当 `coverageRatio < 0.8`、窗口短于 24 小时或存在无法解释的采集缺口时，质量为 `INSUFFICIENT_DATA`。当历史样本触达当时上限或存在相应拒绝时，质量为 `CENSORED_BY_QUOTA`。这两类数据都可以展示，但不能生成降低配额的建议。

样本窗口内出现多个 policy version 时，质量为 `MIXED_POLICY`。报告仍展示观测值，但除非按单一版本重新选择窗口，否则不生成下调建议。

### 4.3 确定性推荐

默认窗口为 7 天，允许 24 小时至 30 天；默认余量为 20%，允许 5% 至 100%。每个资源独立计算：

```text
observedBase = max(currentUsage, historicalPeak)
recommendedLimit = ceil(observedBase * (1 + headroomPercent / 100))
```

规则：

1. 有效样本不足时返回 `NO_RECOMMENDATION / INSUFFICIENT_DATA`。
2. 数据被现有配额截断时，只允许给出“至少保持当前上限”或上调建议，不给出下调建议。
3. `observedBase = 0` 时不建议把无限配额自动改为 0；返回 `NO_RECOMMENDATION / NO_OBSERVED_DEMAND`。
4. 推荐值不得低于当前权威用量。
5. 推荐只作为 proposed value，不自动保存，也不提供批量一键应用。
6. `weight` 只显示启用租户中的相对份额变化，不自动推荐。权重代表业务策略，不是容量统计结果。

风险等级使用稳定语义：

| 等级 | 条件 |
| --- | --- |
| `CRITICAL` | proposed limit 非零且低于当前用量，或 proposed policy 禁用仍有活动工作量的租户 |
| `HIGH` | proposed limit 低于历史峰值，或窗口内有对应拒绝且没有上调 |
| `MEDIUM` | proposed limit 低于带余量建议值，或覆盖率不足 |
| `LOW` | proposed limit 不低于建议值且数据质量充分 |
| `UNKNOWN` | 无足够样本或历史被配额截断，无法作出可靠结论 |

## 5. 用户流程

```text
打开租户治理
  -> 编辑配额
  -> 选择分析窗口和余量
  -> 预览变更
  -> 查看当前影响、历史基线、风险与建议
  -> 调整 proposed policy（可重复预览）
  -> 使用预览时的 expectedVersion 保存
  -> 成功并写入既有审计，或因版本冲突要求重新预览
```

全局报告流程：

```text
租户治理 -> 容量报告 -> 按风险排序/筛选
  -> 查看单租户证据 -> 导出 JSON/CSV -> 回到预览页人工应用
```

## 6. API 契约

### 6.1 单租户预演

```http
POST /api/tenants/{tenantId}/quota-preview
Content-Type: application/json

{
  "expectedVersion": 4,
  "enabled": true,
  "weight": 3,
  "maxConcurrent": 40,
  "maxCpuMillis": 20000,
  "maxMemoryBytes": 34359738368,
  "maxBacklog": 100000,
  "maxTriggerRatePerSecond": 200,
  "window": "P7D",
  "headroomPercent": 20
}
```

响应骨架：

```json
{
  "tenantId": "payments",
  "evaluatedAt": "2026-11-07T08:00:00Z",
  "baseVersion": 4,
  "window": {"from": "...", "to": "...", "coverageRatio": 0.98},
  "overallRisk": "MEDIUM",
  "changes": [{"field": "maxConcurrent", "before": 32, "after": 40}],
  "resources": [{
    "resource": "concurrency",
    "current": 18,
    "average": 12.4,
    "peak": 35,
    "proposedLimit": 40,
    "recommendedLimit": 42,
    "saturationRatio": 0.07,
    "rejections": 3,
    "quality": "COMPLETE",
    "risk": "MEDIUM",
    "reasons": ["PROPOSED_LIMIT_BELOW_RECOMMENDATION"]
  }],
  "warnings": []
}
```

权限为 `ADMIN`。请求是只读计算，不写 Admin 审计；真正的 PUT 继续按现有规则审计 before/after。

稳定错误包括：

- `tenant_not_found`：404；
- `tenant_version_conflict`：409；
- `invalid_capacity_window`：400；
- `invalid_headroom_percent`：400；
- `tenant_capacity_unavailable`：503。

### 6.2 容量报告

```http
GET /api/tenant-capacity?window=P7D&risk=HIGH&cursor=&limit=100
GET /api/tenant-capacity/payments?window=P7D
GET /api/tenant-capacity/export?window=P7D&format=csv
```

列表和详情需要 `READER`，导出需要 `OPERATOR`。列表使用稳定的 `risk desc, tenant_id asc` keyset cursor；`limit` 最大 500。导出设置行数和响应体上限，超过上限返回明确错误，不在 HTTP 线程无限生成。

## 7. 数据与实现边界

### 7.1 领域模型

建议新增：

```text
libs/firefly-domain
  governance/TenantQuotaProposal.java
  governance/TenantCapacityBaseline.java
  governance/TenantCapacityQuality.java
  governance/TenantQuotaRecommendation.java
  governance/TenantQuotaPreview.java

libs/firefly-store-api
  governance/TenantCapacityStore.java

libs/firefly-runtime-support
  governance/TenantQuotaPlanner.java
  governance/TenantCapacityObservationBuffer.java

server/runtime
  TenantCapacitySampler.java

stores/jdbc
  JdbcTenantCapacityStore.java

apis/admin-http
  AdminTenantCapacityController.java
```

`TenantQuotaPlanner` 必须是纯 Java、无 JDBC/HTTP 依赖；给定 policy、usage、baseline、proposal 和时间即可得到确定结果。

### 7.2 观测采集

准入结果已经携带更新后的权威 `TenantUsage`。各节点只在内存中记录该快照、稳定拒绝原因和当前五分钟桶内最大值；不得在每次准入时增加同步 SQL。

每个进程使用启动期唯一 `sourceId`。桶关闭时异步批量刷新；`flushId = sourceId + tenantId + bucketStart`，数据库用 dedupe 记录保证重试不会重复累加。shard 0 maintenance owner 另行批量读取全部权威 usage，填补没有准入事件但仍有在途用量的租户。接管者对同一桶只做 `max` 合并。

缓冲区必须有租户数和待刷新桶数上限。满载、数据库不可用或节点关闭超时时，丢弃规划观测并增加指标；绝不反压 `tryReserve`、Outbox claim 或执行终态事务。

触发速率使用准入决策中返回的全局 `triggerWindowStartedAt + triggersInWindow`。不同节点对同一时间桶取 `max`，不能把节点峰值相加，避免制造不存在的全局峰值。

### 7.3 JDBC feature migration v21

新增两张表，不修改 v1.2.0 的 policy、usage 和 reservation 列：

```text
firefly_tenant_capacity_sample
  tenant_id, bucket_start,
  sample_count,
  min_policy_version, max_policy_version,
  max_active_executions,
  max_reserved_cpu_millis,
  max_reserved_memory_bytes,
  max_backlog,
  max_trigger_rate,
  saturated_concurrency_samples,
  saturated_cpu_samples,
  saturated_memory_samples,
  saturated_backlog_samples,
  saturated_trigger_rate_samples,
  rejected_concurrency,
  rejected_cpu,
  rejected_memory,
  rejected_backlog,
  rejected_trigger_rate,
  rejected_disabled,
  created_at, updated_at
  PK (tenant_id, bucket_start)

firefly_tenant_capacity_flush
  flush_id PK,
  bucket_start,
  created_at
```

索引至少覆盖 `(bucket_start, tenant_id)` 和清理游标。默认桶宽 5 分钟、保留 7 天；允许 1 分钟至 1 小时、1 至 30 天。保留期清理由 shard 0 owner 使用 keyset + bounded batch 执行。

聚合写与 `flush_id` 插入在同一事务内：只有首次插入 flush ID 才能累加拒绝计数；用量字段使用 `max` 合并。这样数据库重试和 HA 接管不会重复计数。

权威 sampler 在同一批读取中取得 policy 与 usage，以当时的上限计算各资源是否达到 90%，并记录最小/最大 policy version。报告不能用“当前上限”反推旧样本是否饱和。

### 7.4 查询与计算

JDBC 在数据库内完成 `count/avg/max/sum`，不把全窗口原始样本全部加载进 Admin 进程。H2、PostgreSQL 和 MySQL 使用相同整数语义；推荐算法不依赖方言特有 percentile 函数。

容量报告只引用租户治理资源，不把各 Gateway 私有连接视图拼成“集群物理容量”。Executor 物理 CPU/内存容量规划需要独立的共享快照模型，不在 v1.2.1 伪造结果。

## 8. Admin UI

租户编辑对话框增加两个动作：

- `预览变更`：默认动作，打开风险面板；
- `直接保存`：保留给紧急操作，但当风险为 `CRITICAL` 时要求二次确认并展示原因。

风险面板按资源展示“当前 / 平均 / 峰值 / proposed / 推荐”，并显示覆盖率、采样窗口和数据质量。所有颜色同时配合文字与图标，不只靠颜色表达风险。

租户治理页增加“容量报告”子视图，支持：

- 风险、启停、无限配额、数据质量筛选；
- 按风险、触顶比例、拒绝数排序；
- 查看证据并回到对应租户编辑；
- 有界 JSON/CSV 导出。

推荐值必须由用户逐项勾选后带回表单，不能自动提交。

## 9. 指标与告警

新增低基数指标：

```text
firefly_tenant_capacity_observations_dropped_total{reason}
firefly_tenant_capacity_flush_failures_total{reason}
firefly_tenant_capacity_flush_lag_seconds
firefly_tenant_capacity_samples{quality}
firefly_tenant_quota_preview_total{risk}
```

不把 tenantId 放入新增的采集健康指标，避免租户数扩大 Prometheus 基数。现有按 tenant 的 usage/quota/rejection 指标保持不变。

默认告警覆盖采集刷新持续失败、刷新延迟超过两个桶和观测缓冲丢弃；规划链路故障不得升级为调度不可用告警。

## 10. 兼容、升级与回滚

- v21 是 additive feature migration；不改变 `JdbcSchema.CURRENT_VERSION = 12` 的核心兼容约定。
- 1.2.0 节点忽略新表，继续使用原有 policy、usage 和 reservation。
- 滚动升级期间可以采样，但容量报告标记 `MIXED_VERSION`，完成全部节点升级并积累一个完整窗口前不输出下调建议。
- Admin 新接口独立增加；现有 `GET/PUT /api/tenants` 请求和响应保持兼容。
- Executor v1/v2、任务定义、Outbox、执行状态机和公平调度语义不变。
- 回滚到 1.2.0 时停止 sampler 即可；新表可以保留，不需要破坏性降级迁移。

## 11. 明确非目标

- 不自动应用推荐，不定时修改配额，不做闭环自治。
- 不用机器学习预测未来增长，不把历史峰值描述成 SLA 保证。
- 不实现运行中任务强抢占。
- 不新增层级租户、部门配额、共享池、突发积分或计费。
- 不修改加权公平队列算法，不自动推荐业务权重。
- 不实现物理 Executor 集群容量承诺。
- 不做 HTTP Executor、Python/Go SDK、任意 DAG、远程节假日 Provider、S3/OSS。

## 12. 验收矩阵

### 12.1 正确性

- proposal 低于当前并发/CPU/内存/backlog/触发用量时逐维度返回 `CRITICAL`。
- proposal 为 0 时按“不限制”解释，不产生除零或错误的饱和率。
- disabled 租户仍有 backlog 或 active execution 时明确提示“不抢占，只拒绝新准入”。
- 数据不足和被配额截断时不生成下调建议。
- 相同 policy、usage、baseline、proposal 和时钟得到字节级稳定的语义结果。
- 预览不改变 policy version、usage version、reservation 数量、Outbox 或审计数量。

### 12.2 HA 与一致性

- 两个节点刷新同一桶时 maxima 合并正确，拒绝计数不因重试重复。
- shard 0 owner 在桶中途失联，新 owner 接管后不覆盖更高观测值。
- source 重试同一 flush ID 为幂等；新 source 不与旧进程冲突。
- policy 在预览后并发更新时，旧 expectedVersion 无法应用。
- maintenance 清理与报告查询并发执行，不锁住准入表。

### 12.3 规模与故障

- 1,000 租户、7 天、5 分钟桶的报告在目标性能内，内存使用有界。
- 观测缓冲满、数据库中断和 Admin 客户端取消请求时，准入与派发继续工作。
- 导出超过行数或响应体上限时快速失败，不产生无界内存或临时文件。
- 1.2.0/1.2.1 混合节点滚动期间无准入失败、无重复派发、无错误下调建议。

### 12.4 非 Docker 验证入口

本版本的默认开发和验收流程不依赖 Docker：

- 纯领域算法使用单元测试和固定时钟；
- JDBC 迁移、聚合和幂等使用 H2 测试；
- Admin API、RBAC、审计和 UI 使用现有 Gradle/Playwright 测试；
- PostgreSQL/MySQL 验证连接到显式提供的外部测试库，由 CI secret 或本地连接参数驱动，不使用 Testcontainers；
- 未配置外部数据库时，报告为“真实数据库门禁未执行”，不得伪装为通过。

## 13. 实施拆分

建议按可独立评审的顺序交付：

1. **领域契约与 planner**：proposal、baseline、quality、recommendation、preview 和纯算法测试。
2. **容量存储**：v21 migration、JDBC 聚合、flush dedupe、保留期清理和 H2 测试。
3. **运行时采集**：有界 observation buffer、异步刷新、shard 0 权威采样、指标和 HA 测试。
4. **Admin API**：单租户 preview、容量报告、导出、RBAC、错误码和版本竞态测试。
5. **Admin UI**：预览—应用流程、风险面板、报告页、无障碍和 Playwright E2E。
6. **兼容与发布门禁**：1.2.0 滚动矩阵、外部 PostgreSQL/MySQL job、升级/回滚文档和版本发布检查。

实施预算按中等规模控制，预留 20% 用于查询性能和跨方言差异。若持久化观测或全租户报告无法在目标性能内完成，优先保留“单租户 dry-run + 有界基线”，不得用自动推荐或无限查询换取表面完整度。
